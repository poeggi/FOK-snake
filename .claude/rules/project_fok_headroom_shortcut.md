# NON-NEGOTIABLE duel pairing: 1-tick input headroom + the peer tk==simTick shortcut

The 1vs1 duel lockstep has a MANDATORY design pairing. Both halves must exist together; removing or "simplifying" either breaks the link. Annotated in-code as "HEADROOM here" / "SHORTCUT here" markers.

Half 1 -- HEADROOM (js/duel-core.js `netLocalInput`). Every local input is authored at least ONE tick in the FUTURE (never at simTick or earlier) and sent at once: dir at `simTick + _gDue` (next step boundary, always >= simTick+1), boost/boostend at `simTick+1` (tightest lead). That one-tick lead IS the network transmit headroom -- the window for the peer to receive it and apply it on its own timeline before its sim reaches the authored tick, so the common case costs no rollback. Authoring at the current tick gives the wire zero time => a rollback on every input. Do NOT widen the lead (1 tick suffices), and do NOT collapse it to simTick.

Half 2 -- SHORTCUT (js/duel-core.js `_netPeerInput`). The one-tick-late live-apply is how the peer SPENDS that headroom. When an arriving peer input has `tk === simTick` (the tick that just ran), inject it live (`simCommand`) and skip the rollback, but ONLY if that tick did not already consume it: dir -> `!_rbPeerSteppedSince(oP, tk)`; boost -> `tk > _gAt`. This is the ONLY lockstep-safe live-apply case: simTick is the newest past tick, so no future rollback can start later than it (the log entry is always re-applied, never skipped) and no stale intermediate snapshots exist. A general past-input live-apply is UNSOUND (a later rollback starting after the input's tick replays from there and silently drops it) -- that was the original duel-desync boost/dir bug. Everything older than one tick, or a tick that already stepped/accrued, must go through ONE batched rollback+replay in netTickPre.

Validated: `node test/duel-desync.js` rollbacks fell clean 26->3 / lossy 57->34 / long 147->39 with convergence held (conv=yes, selfJumps=0, desync=0/0, lost=0).

"Sent at once" is real code, guarded by a discriminating test:
- One-shot repair resend (`_netInRepeat`) -- the next input-free netTickPre repeats the last input flush ONCE (repairs single datagram loss in ~17ms vs 267ms heartbeat).
- Leading-edge input flush -- the dir branch of netLocalInput ships the packet AT authoring, capped by `_netInFlush` (js/duel-core.js) at ONE input flush per tick cycle (touch-spam collapse preserved). Without this, the record waited for the next netTickPre (~1 tick of pure added latency on every turn).
- The `headroom subtick 0rb` scenario (test/duel-desync.js) is discriminating. Why it used to be blind: the driver authored steers pre-tick (the same boundary's flush shipped them, zero in-model deferral) AND autopilot intents are born right after a game step, at MAXIMUM _gDue (view only changes on steps) -- a double best-case. Post-tick authoring ALONE does not fix it; the steer must be HELD to the last interval before its target boundary (`_gDue==1`, same target => pilot undegraded, wire budget minimal). Driver opts: `postAuthor` (hold-to-_gDue==1) + `doubleEvery` (every 3rd intent = steer + sim-rejected reverse at birth, needs _gDue>=2 because the capped 2nd record ships a tick later). Proof: the pre-fix code fails the lane with rb=191 HEADROOM LEAK; the fixed code passes with rb=0. Do not weaken this lane.
